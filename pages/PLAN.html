jitmodel — Implementation Plan

A web application (jitmodel) that models the cryogenic power cycle described in US Patent 11,598,261. The cycle uses LNG or liquid air, pumps it to supercritical pressure, and expands it through a turbine. It then re-condenses the expanded stream against the incoming pumped liquid in a shared gasifying/condensing heat exchanger, re-pumps it, re-heats it and expands it a second time. The app must support real engineering use: design-point sizing, sensitivity studies, and hourly dispatch economics.

Before starting: put the patent PDF at docs/US11598261.pdf and read it. Every “patent reference value” below must be checked against the PDF. If the PDF disagrees with this plan, the PDF wins; note the discrepancy in docs/DECISIONS.md.

0. Working rules for this session

  1. Work one phase at a time, in order. Don’t start a phase until the previous phase’s acceptance checks pass.
  2. Run the tests after every meaningful change (make test, which runs .venv/bin/pytest). Commit at the end of each phase with a message like phase 3: discretized HX + pinch solver.
  3. Never invent performance numbers. Anything not computed by the solver or taken from the patent shows — in the UI. Test fixtures may use patent values only, each with a comment citing the figure or column.
  4. Units: use SI internally (Pa, K, J/kg, kg/s, W). Convert to US customary (psia, °F, Btu/lb, lb/h, MW) only at the API/UI boundary, through one units.py module. Include a UI toggle for SI vs. US customary.
  5. Dependencies: use only those listed in §2. Ask before adding anything else. Vet every Python package on PyPI before downloading it (name spelling, source repo, release history, who requires it) to guard against typosquatting; see CLAUDE.md rule 8.
  6. Record non-obvious modeling choices in docs/DECISIONS.md, one short entry per decision.
  7. Copy these rules into CLAUDE.md at the repo root during Phase 0.

1. What the patent describes (modeling summary)

Core loop (every figure uses this):

  1. TK-1 storage tank holds cryogenic liquid near atmospheric pressure.
  2. P-1 pumps it to supercritical pressure (patent range about 1000–2500 psia).
  3. E-1, the gasifying/condensing heat exchanger. On its cold side, the pumped liquid is heated into a superheated supercritical fluid. On its hot side, the expanded vapor from T-1 condenses back to liquid, with no external coolant.
  4. E-2 warming heat exchanger (ambient air, seawater, or an ORC condenser) raises the fluid to about 50–100 °F.
  5. H-1 heater uses the case’s heat source.
  6. T-1 expander expands the fluid to the intermediate pressure and drives a generator.
  7. E-3 recuperator cools the T-1 exhaust before it enters the hot side of E-1.
  8. V-1 accumulator holds the re-condensed liquid at intermediate pressure.
  9. P-2 re-pumps it to supercritical pressure.
  10. H-2 re-heats it.
  11. T-2 expands it to final pressure: the gas pipeline for LNG, or atmosphere/combustion air for liquid air.

Patent reference values (verify in PDF):

Quantity LNG Liquid air
Intermediate (re-condensing) pressure ≈ 520 psia ≈ 455 psia
Re-condensed temperature not stated (compute) ≈ −230 °F
Supercritical pump discharge 1000–2500 psia 1000–2500 psia

Case presets:

  • Fig. 1: LNG regasification with double expansion. Heat comes from gas turbine exhaust.
  • Fig. 2: Liquid air with a methane Rankine loop, plus combustion turbine and duct burner heat.
  • Fig. 3: Liquid air with a reciprocating engine run with its turbocharger bypassed, plus an ORC on the exhaust.
  • Fig. 4 / 4A: Liquid air with high-temperature gas turbine exhaust and an ORC. The patent claims a large increase over the gas turbine’s standalone output; verify the figure in the PDF and use it only as a sanity check.
  • Fig. 5: LNG combined gas and power storage. Heat comes from engine exhaust and turbocharger air.

Baseline for comparison: a conventional direct-expansion cycle (pump → heat → single expansion → out) using the same fluid, pressures and heat source. Every result screen shows the gain versus this baseline.

The central numerical problem: the intermediate pressure is fixed by an internal pinch in E-1, not by the cold-end temperature. The hot stream’s condensing plateau has to fit against the cold stream’s supercritical heat-capacity spike. A lower intermediate pressure gives more T-1 work, but below some point the exchanger can’t close. So the solver finds the lowest intermediate pressure at which the minimum temperature difference along the discretized exchanger is ≥ ΔT_min, with the hot stream fully condensed at the outlet.

2. Stack

A regular server-rendered web app: Flask + Jinja templates + plain HTML/CSS + small vanilla JavaScript files. No Node, no npm, no bundler, no build step, no client-side framework (no React, Vue, etc.).

Python (3.13 from Debian apt, python3 -m venv + pip)

  • The virtualenv lives at .venv in the repo root (git-ignored). Create it with python3 -m venv .venv, then install with .venv/bin/pip install -e '.[dev]'. Never install into system Python.
  • Dependencies are declared in pyproject.toml (runtime in dependencies, test/lint tools in the dev extra). No lock tool; pin minimum versions.

Runtime:

  • CoolProp for real-fluid properties. Use the AbstractState API with the HEOS backend. Allow BICUBIC&HEOS as an optional speed mode. Model methane as pure Methane in v1 and air as pseudo-pure Air. Put all property calls behind an interface so REFPROP or GERG-2008 mixtures can be added later.
  • numpy and scipy (brentq, root, and linprog with the HiGHS method).
  • pydantic v2 for all input/output schemas.
  • flask (brings Jinja2 and Werkzeug) for pages, form handling, file upload and the small JSON endpoints.
  • pandas for dispatch time series only.

Dev/test (dev extra):

  • pytest and hypothesis for tests; Flask’s built-in test client for route tests.
  • ruff (lint + format check) and mypy --strict for type checks on core/.
  • playwright (Python package) for one end-to-end smoke test, driving the apt-installed /usr/bin/chromium via executable_path. Never run playwright install.

Browser side (static files, no package manager)

  • Plotly.js for the T–Q, T–s, sweep and dispatch charts. Download one pinned plotly-<version>.min.js once into jitmodel/web/static/vendor/ and commit it. Record the version, source URL and SHA-256 in docs/DECISIONS.md. No CDN at runtime.
  • IBM Plex Sans / Mono fonts (OFL), vendored as woff2 in static/fonts/, with system-font fallback.
  • Plain CSS with design tokens (§7) in static/css/. No UI kit, no preprocessor.
  • Plain JavaScript (ES modules loaded with <script type="module">), one small file per page. JS only improves pages that already work without it: live slider preview, drawing charts from JSON embedded in the page, click-to-inspect, and polling a running job. Every action has a normal HTML form fallback.

Dev server: single port 5001, dev instance only

  • make dev runs flask --app jitmodel.web run --debug --host 0.0.0.0 --port 5001. One process serves the pages, static files and JSON endpoints. It’s bound to 0.0.0.0 with no auth, so use it on a trusted network only.
  • No production server, build step or deployment is in scope.

4. Phases

Phase 0 — Scaffold

  • git init, .gitignore (.venv/, var/, caches), and the layout above.
  • CLAUDE.md, pyproject.toml, and a plain git pre-commit hook in .githooks/pre-commit that runs make lint, enabled with git config core.hooksPath .githooks. Don’t use the pre-commit framework.
  • Makefile targets:
    • make setup creates .venv and runs pip install -e '.[dev]'.
    • make dev starts the port-5001 dev server (§2).
    • make test runs pytest; make e2e runs the Playwright smoke test separately.
    • make lint runs ruff check, ruff format --check and mypy --strict jitmodel/core. All targets call tools through .venv/bin/.
  • A minimal create_app() with one page that renders base.html and the tokens.
  • Done when: make test and make lint pass on the skeleton, and make dev serves the placeholder page on port 5001.

Phase 1 — Properties layer

  • props/base.py: a FluidProps protocol with state_ph(P, h), state_pt(P, T), state_ps(P, s), sat_liquid_T(T), sat_liquid_P(P), critical(). Each returns an immutable ThermoState with T, P, h, s, rho, cp, phase and quality.
  • coolprop_impl.py: implement this with AbstractState. Handle states near the critical point by imposing the phase explicitly where CoolProp is unreliable. Cache states with an LRU cache keyed on rounded inputs.
  • Tests:
    • Round-trip P,T → h → P,h → T to within 1e-6 relative, across 90–700 K and 0.1–20 MPa for both fluids. Use hypothesis, excluding a small band around the critical point.
    • Critical points match the CoolProp reference values.
  • Done when: tests pass and 10k state_ph calls finish in under 1 s in HEOS mode (the benchmark is marked slow).

Phase 2 — Unit operations

  • Stream: fluid, m_dot, P, h, with derived T, s and phase.
  • Pump and Expander: take outlet pressure and isentropic efficiency; return the outlet stream and shaft power. Expanders also take a generator efficiency.
  • Heater: set an outlet temperature, or a duty, or a coupling to a heat-source stream (see Phase 5).
  • Splitter, Mixer, Accumulator (pass-through with a saturated-liquid check), Source, Sink.
  • Tests: energy balance closes to 1e-9 relative on every unit; an isentropic efficiency of 1.0 gives Δs ≈ 0.

Phase 3 — Discretized counterflow HX and pinch

  • hx.py: split the exchanger into N equal-duty segments (default N = 200). For each segment boundary, compute hot and cold enthalpies, get temperatures from the property layer, and return the T–Q profile, the minimum ΔT, and the pinch location.
  • Support three modes: (a) both inlets plus hot outlet enthalpy → solve cold outlet; (b) both inlets plus a ΔT_min target → solve the maximum duty; (c) a UA rating mode (stretch goal).
  • intermediate.py: given the P-1 discharge state, the T-1 inlet state, the expander efficiency and ΔT_min, find the lowest intermediate pressure such that:
    • the hot stream leaves E-1 as saturated or subcooled liquid, and
    • min ΔT along E-1 ≥ ΔT_min. Use brentq over pressure, bracketed between a safe lower bound and just under the critical pressure (or the cricondentherm for air). Return the T–Q profile for plotting.
  • Tests:
    • A synthetic ideal-gas case with an analytic answer.
    • Validation: intermediate_pressure for the liquid-air and LNG presets lands within ±10% of the patent values (≈455 and ≈520 psia) under the patent’s stated conditions. Log the actual values and conditions in docs/VALIDATION.md.
  • Done when: both validation tests pass, or any gap is explained in VALIDATION.md with the assumptions that differ.

Phase 4 — Flowsheet solver and Fig. 1

  • flowsheet.py: a directed graph of units and streams. Stream IDs mirror the patent’s reference numbers where practical.
    • Solve in sequential-modular order.
    • Detect recycles automatically and choose tear streams.
    • Converge with Wegstein iteration and fall back to Broyden (scipy.optimize.root).
    • Report iteration count, residuals and a convergence status.
  • cases/fig1.py: builds the Fig. 1 flowsheet from a pydantic CaseInputs.
  • baseline.py: builds the matching single-expansion baseline.
  • Outputs (a pydantic CycleResult): every stream’s state, every unit’s power and duty, net power, pump work, heat input, fuel heat rate (where fuel is used), specific output (kWh per tonne of cryogen), gain versus baseline, and the E-1 T–Q profile.
  • Tests: global energy balance closes; the solver converges from three different initial guesses; results are identical across runs.

Phase 5 — Remaining presets and heat sources

  • heat_sources.py: exhaust streams (gas turbine or engine) with temperature, mass flow and composition, and h(T) from an ideal-gas mixture. Also molten salt (constant cp) and a duct burner (fuel flow → temperature rise, fixed LHV).
  • Presets:
    • fig2.py: liquid air plus a closed methane Rankine loop.
    • fig3.py: engine exhaust plus an ORC. Make the ORC fluid configurable, defaulting to one named in the patent.
    • fig4.py: gas turbine exhaust plus ORC with an exhaust split fraction. Verify the patent’s split range.
    • fig5.py: LNG plus engine and turbocharger air.
  • Tests: each preset converges at default inputs, closes its energy balance, and beats its baseline’s net power. If one doesn’t, record it in VALIDATION.md rather than tuning inputs to force it.

Phase 6 — Studies

  • sweep.py: 1-D and 2-D parameter sweeps over any numeric input. Run them in parallel with concurrent.futures and return tidy tables.
  • optimize.py: maximize net power (or specific output) over a chosen set of inputs within bounds, using scipy.optimize.minimize (SLSQP) with multiple starting points. Converge E-1 inside each objective evaluation.
  • Done when: the P-1 discharge sweep for Fig. 1 produces a smooth curve with no solver failures across 1000–2500 psia.

Phase 7 — Dispatch and economics

  • Inputs: an 8760-row hourly price CSV, fuel price, tank capacity, liquefaction power and specific energy (user-supplied; never hard-coded), discharge case (whose power and fuel figures come from the solved cycle), and a pipeline send-out limit for LNG.
  • Dispatch rules:
    • Price threshold: discharge when price is above X, charge when below Y.
    • Fixed daily window: default discharge window 18:00–22:00. Verify this against the patent’s peak-period description.
    • Perfect-foresight LP: linprog with HiGHS; variables are charge/discharge per hour and tank level; constraints are capacity, power limits and send-out limit.
  • Outputs: hourly schedule, tank level, annual net revenue, discharge hours per year, energy ratio, fuel heat rate.
  • Tests: the LP matches brute force on a 48-hour toy case; the tank never exceeds its limits.

Phase 8 — Web routes, jobs and JSON endpoints

Flask app built with create_app(). Form data and JSON are both validated with the pydantic schemas in schemas.py. Every form field maps to a CaseInputs field, converted to SI through units.py.

HTML routes (Post/Redirect/Get):

  • GET / redirects to /flowsheet?case=fig1.
  • GET /flowsheet?case=… renders the input form with the preset defaults.
  • POST /solve validates the form and starts a solve job. It redirects to /results/<id>.
  • GET /results/<id> shows a “Solving…” page (with <meta http-equiv="refresh" content="1"> for the no-JS fallback) until the job is done. Then it shows the full flowsheet page with results.
  • GET /heat-exchangers/<id>, GET /sweeps, POST /sweeps, GET /dispatch, POST /dispatch (multipart CSV upload through Flask’s request.files).
  • GET /export/<id>.csv and GET /export/<id>.json.
  • Units: ?units=si|us, remembered in a cookie. Conversion happens only when rendering, through units.py Jinja filters.

JSON routes (under /api, used only by the page scripts for live updates):

  • GET /api/cases lists presets with their default inputs.
  • POST /api/intermediate runs just the E-1 intermediate-pressure solve for live slider feedback. It returns the pressure, temperature and T–Q profile.
  • GET /api/jobs/<id> returns the job status and, once done, a link to the result.

Jobs: solves, sweeps, optimizations and dispatch runs go through jobs.py, which uses a concurrent.futures process pool (the dev server is a single process). Results are saved as JSON in var/results/<id>.json, so they survive dev-server reloads.

Errors: JSON errors are {code, message, detail}. HTML errors re-render the form with the message next to the field that caused it.

Tests (Flask test client): every route returns 200/302 as expected; invalid input re-renders with errors; unsolved pages show —.

Done when: a solve through POST /solve gives a stored CycleResult that matches a direct Python solve bit-for-bit.

Phase 9 — Pages and UI

Server-rendered Jinja pages styled with the §7 tokens (there is no separate mockup). Each page is a normal HTML page with forms. A small per-page JS file adds live behavior on top. Pages:

  1. Flowsheet (flowsheet.html)
    • Left panel: a form with the case preset select, the LNG / liquid air choice (radio buttons styled as a segmented control, set by the preset), and range sliders (<input type="range"> with a paired number box) for P-1 discharge, P-2 discharge, min HX approach and expander efficiency. Buttons: Solve cycle (submits the form), “Compare to baseline” (a link to the baseline section of the results) and “Export” (links to CSV/JSON).
    • Center: the flowsheet as inline SVG rendered on the server by diagram.py from the case’s layout. Pass 1 runs along the top and pass 2 along the bottom, and E-1 spans both rows. Streams are colored by temperature (cold, warm, hot tokens). Each unit is a focusable <a>/<button> in the SVG. Clicking it (or pressing Enter) shows that unit in the inspector. Without JS, it links to ?unit=<id>.
    • Below the diagram: the E-1 T–Q composite (Plotly) with the pinch marked, and an intermediate-pressure card.
    • Right panel: the inspector (unit description plus a stream/unit table) and the results grid: net power, pump work, T-1, T-2, fuel heat rate, specific output, and gain versus baseline.
    • Header: the status text (“Not solved”, “Solving…”, “Converged in N iterations”, “Failed: reason”) and the tabs.
    • flowsheet.js: when a slider moves, POST the form to /api/intermediate after a 250 ms debounce and update the T–Q chart and the intermediate-pressure card. A full solve only happens on Solve cycle. While a job runs, poll /api/jobs/<id> and load the result page when it’s done. Without JS, the meta-refresh fallback does the same.
  2. Heat exchangers: T–Q plots for every exchanger, plus a T–s diagram with the saturation dome and the cycle overlaid. The data is embedded in the page as JSON (<script type="application/json">) and drawn by charts.js.
  3. Sweeps: a form to pick one or two inputs and their ranges. Submitting runs a job. The result page shows a line chart or heatmap and a table. Each table row (and each chart point, via JS) links to /flowsheet with those inputs filled in.
  4. Dispatch & economics: a multipart form for the CSV upload, market and asset inputs, and the dispatch rule. The result page shows a typical-day price chart with the charge/discharge windows shaded, a tank-level chart, a KPI row, a schedule table (paginated on the server) and a CSV download link.

UI rules

  • Any result not yet computed shows —. Illustrative charts are labeled “Illustrative until solved”.
  • Keyboard accessible: real buttons, inputs and labels; aria-label on icon-only buttons.
  • Works without JS for every action (solve, sweep, dispatch, export). JS only adds live preview, charts, click-to-inspect and polling. Without JS, charts fall back to data tables.
  • No inline event handlers and no JS frameworks. Each page loads only its own module plus charts.js and the vendored Plotly.
  • Web app only. Minimum supported width is 1280 px. Add a read-only results layout below 768 px as a stretch goal.

Done when: the Playwright smoke test (Python, system Chromium, run by make e2e) passes: load Fig. 1 → move the P-1 slider → solve → the results grid fills in → switch to Dispatch → upload a fixture CSV → the KPIs fill in.

5. Validation checklist (docs/VALIDATION.md)

For each preset, record the inputs used, the computed intermediate pressure and temperature, the net power, the gain versus baseline, the energy balance residual, and the patent value it’s compared against (with figure/column reference). Pass criteria:

  • Intermediate pressure within ±10% of the patent value where the patent gives one.
  • Energy balance residual below 1e-6 relative.
  • The double-expansion cycle beats its baseline.

6. Known modeling risks

  • Near-critical property behavior: cp spikes and CoolProp flash failures. Mitigate with an explicit phase, a finer HX discretization near the pseudocritical temperature (adaptive refinement where cp changes fast), and clear error messages.
  • Air as a pseudo-pure fluid: CoolProp’s pseudo-pure Air has an ancillary-based bubble/dew glide, but its two-phase flashes need workarounds (D21) and it is not a true mixture model (no composition shift between phases). Add an optional N₂/O₂/Ar mixture later.
  • LNG as pure methane: this understates the condensing glide. Keep the property interface mixture-ready.
  • Recycle convergence: start the tear-stream guess from the baseline solution.
  • Freedom to operate: this project models a patented process. Add a README note that commercial use may need a license and legal review.
